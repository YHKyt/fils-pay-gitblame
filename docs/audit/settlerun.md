# Settlement daily run and daemon schedule

Scope: `apps/settlement/internal/settlement/batch.go` (`RunDailyBatch` loop) and `apps/settlement/internal/scheduler/daemon.go`. Same format as the other notes in this folder. Go suite: `cd apps/settlement && DATABASE_URL=… go test -p 1 ./...`.

## One merchant's error stopped the whole daily run — High

**Where:** `apps/settlement/internal/settlement/batch.go` (`RunDailyBatch`: four `return report, fmt.Errorf(...)` on `CloseBatch`, `IsSplitParent`, `PayoutSplitBatch`, `PayoutBatch` errors), `apps/settlement/internal/scheduler/daemon.go` (`runIfDue` returned on that error and only ever retries "yesterday")
**Evidence:** three active merchants each capture 100,000 fils on 2026-02-17. The middle one in id order is a split parent whose weights sum to 5000, so `PayoutSplitBatch` refuses it (`ErrSplitWeightsNotWhole`). On the old code a full `RunDailyBatch(date, nil)` stopped there: `merchant 58005682-… missing from the report: a failure earlier in the run blocked it` (`TestRunDailyBatch_OneMerchantFailureDoesNotBlockOthers`). On a database left with one such broken merchant, the old code failed every later full run on that merchant's error, whatever the date.

- **What:** the loop returned on the first merchant error. It skipped only `ErrMerchantNotEligible`. Every merchant after the failing one, in id order, was neither closed nor paid.
- **Why:** the merchants are independent: each one's close and payout are their own transactions, so nothing about merchant N's failure makes merchant N+1 unsafe to settle. The early return turned a per-merchant problem into a platform-wide one. The daemon then logged the error, returned (skipping payout notifications too), and on later days only looked at the new "yesterday", so the blocked merchants' day was never retried without a manual `run-batch --date` backfill.
- **Breaks:** one misconfigured merchant (bad split weights, a constraint error, a failed payout record) means every merchant sorting after it is not paid that day, and it repeats every day while the bad merchant stays broken. Merchants are paid late and do not know why.
- **Fix:** the loop records each failure, moves on to the next merchant, and returns `errors.Join(failures...)` with the report of the merchants that did settle. It stops early only if `ctx` is cancelled (shutdown). The daemon logs the error but no longer returns, so it still logs the count and enqueues `settlement.paid` events for the batches that were paid. The failed merchant's batch stays `closed`, and the next tick retries it. This is the smallest change: four `return` lines become `append` + `continue`, plus one `ctx` check and the final `errors.Join`. The error type and the report shape are unchanged, so callers keep working: the CLI still exits non-zero, and the internal API still answers 500.
- **Test:** `internal/settlement/batch_run_isolation_test.go`: merchants 1 and 3 are in the report with net 97,500, payout legs of 97,500 and `merchant_payable` 0. The error wraps `ErrSplitWeightsNotWhole` and names the bad merchant, which is not in the report, and its batch stays `closed`. Old code: fails (`missing from the report`). New code: passes.

## The nightly 02:00 balance-cache refresh never ran — Low-Medium

**Where:** `apps/settlement/internal/scheduler/daemon.go` (`Run` called only `runIfDue`); promised by `docs/ARCHITECTURE.md:41-42` ("The daemon also refreshes it at 02:00 Bahrain time") and `docs/ADMIN.md:87` ("The nightly recompute does the same thing at 02:00")
**Evidence:** no code path in the daemon touched `merchant_balances` apart from batch moves. A cache drifted to 99,999 fils for a merchant whose `merchant_payable` ledger balance is 40,000 stays 99,999 indefinitely. With the fix, the first wake at 02:05 Bahrain rewrites it to 40,000 (`TestRefreshBalancesIfDue_NightlyAt0200Bahrain`).

- **What:** the documented nightly recompute did not exist. Operators and support were told that a bad cached balance corrects itself overnight. It did not.
- **Why:** the cache (`merchant_balances.cached_payable_fils`) mirrors the `merchant_payable` ledger account, and it drifts whenever an incremental move is missed or a cache-only adjustment is made. The docs relied on a nightly rebuild to bound that drift to one day.
- **Breaks:** dashboards and payout estimates read the cache, so drift persisted until someone ran `rebuild-balances` or pressed the console button.
- **Fix:** `refreshBalancesIfDue` runs `ledger.RefreshBalanceCache`, the same refresh as the console's **Rebuild cached balances** button. It runs on the first daemon wake at or after 02:00 Asia/Bahrain, at most once per business day. The last-run day is kept in memory, so a restart after 02:00 refreshes once more, which is harmless. A failure is logged and retried on the next wake. No migration and no new config: it reuses the existing refresh and the daemon's existing ticker.
- **Double counting:** the refresh overwrites the cache with the ledger balance; it never adds, so repeats are safe. It is only correct if every `merchant_payable` posting moves the cache by the same amount in the same transaction. On the current base, captures do not move the cache and `CloseBatch` adds the batch net instead, so a rebuild between a capture and its close counts that capture twice. The console button has the same problem today. `agent/settlebal` (f392013) fixes that cache definition, and its lock change (cb92543) keeps the refresh from overwriting an in-flight move. **Merge `agent/settlebal` before or together with this change.** I checked by test-merging `agent/settlebal` into this branch (not committed): this refresh test, the run-isolation test and settlebal's `TestBalanceCache_MatchesLedgerThroughCaptureRebuildCloseAndPayout` all pass. ADR-0006's cache-only "display adjustments" are now reset every night. ADR-0006 already says a rebuild resets them, and they are not money, so this is the documented behaviour.
- **Test:** `internal/scheduler/balance_refresh_test.go`: at 01:59 Bahrain nothing changes. At 02:05 the cache becomes 40,000. A second wake the same day does not refresh again (the cache is re-drifted and stays 99,999). The next day at 02:00 it refreshes again. Old code: `undefined: refreshBalancesIfDue` (the feature did not exist). New code: passes.
